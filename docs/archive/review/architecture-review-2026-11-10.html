1 · The parse vocabulary is hand-duplicated 3×

Strong

Files: src/lib/server/services/naturalLanguageService.ts (2684 ln) · src/lib/utils/taskQuickAdd.ts (599) · apps/android/.../domain/tasks/TaskQuickAdd.kt (309, header says "Port of src/lib/utils/taskQuickAdd.ts… Test vectors mirror taskQuickAdd.test.ts") · support: dateParsing.ts, dateResolution.ts, dateVocab.ts.

Problem: the same day-phrase/roster/priority vocabulary is maintained three times by hand; MONTH_INDEX is rebuilt inside Kotlin even though dateVocab.ts is nominally the source of truth. naturalLanguageService.ts carries ~150 lines of ORDINAL_WORD_MAP plus an inline editDistance — a shallow module: the interface is about as complex as the implementation, everything is one-off plumbing around compromise + regex.

Solution: make the test-vector file the seam, not the code: one shared JSON of parse cases consumed by taskQuickAdd.test.ts, TaskQuickAddTest.kt and QuickParseContractTest.kt; the Kotlin port shrinks to an interpreter over shared vectors; fold ORDINAL_*, TOD_TIMES, fuzzyDayToken into dateVocab.ts so "all three parsers" have one address.

Benefits: highest leverage in the repo: a parse regression can't resurface per-platform; every affected test already exists (contract tests are the seam, guarded today). Plus AI-navigability: one vocabulary file instead of three synchronized constants.

2 · Two back-stacks, one "back" concept (Android route vs sheet)

Worth exploring

Files: apps/android/…/ui/nav/AppNav.kt · apps/android/…/ui/calendar/CalendarViewModel.kt (~21 public functions, @Suppress("TooManyFunctions")).

Problem: "Back" is split over three owners: AppNav.back() (screen), CalendarViewModel.back()/viewBeforeDay (view), and system-back wiring in FamilyPlanzHost. The sheet: CalendarSheet overlay machine re-implements navigation inside the VM without participating in back history. The VM's interface mirrors its fields — shallow god-module.

Solution: deepen CalendarUiState into a small overlay: Stack<CalendarOverlay>: cellTap/openSheet/closeSheet/back/setSelectionMode collapse into push/pop; viewBeforeDay dies; AppNav stays a real seam (it is already test-driven standalone).

Benefits: one back concept, one set of tests: AppNavTest, BackNavUiTest, ShellNavUiTest, DayViewRangeSelectTest all survive nearly unchanged because they pin contracts, not field placement. #292/test-suite floor keeps working.

3 · Day Dashboard: one good seam — stop wide-mirroring the wires into props

Worth exploring

Files: src/lib/server/db/actions/dashboard.ts · src/lib/server/services/dashboardData.ts (deep: one composition seam serving +page and GET /api/dashboard — keep it) · src/lib/components/dashboard/DayDashboard.svelte.

Problem: the leak is downstream: DayDashboard re-declares the full wire shape (tasks 8 fields, watch out for the assignment gaps), and openEvent needs a chained as unknown as Event cast + oxlint suppression because GlanceEvent ⊄ Event.

Solution: let loadDashboard return a typed DashboardModel and have cards type props as DashboardModel['kidsSchedule'] — one definition, zero casts; RankableTask's drift goes back to taskPriority.ts.

Benefits: empathy not needed: pure type-level, all 6 card tests + 2 server tests survive. The next card addition stops needing a bounce across 4 files.

5 · Recurrence/rollover vocabulary furcated (3 weekday enums)

Speculative

Files: naturalLanguageService.ts (`MONTH_MAP`, `WEEK_ORDER`), taskQuickAdd.ts/dateResolution.ts (resolver), dateVocab.ts ("source of truth" that isn't), Kotlin takeover.

Problem: three weekday/mo-day token tables coexist, and the Kotlin lookup matches by 3-letter prefix — a rule that silently diverges. The rollover rule itself is centralized (good); the vocabulary around it isn't.

Top recommendation

Do #1, the shared parse vectors + one dateVocab first: 3 languages of the same grammar are the highest leverage (a parse regression stops being triple-dangerous) at the lowest risk — it's purely additive wrappers over already-tested code paths, no semantic risk, and contract tests around the wire IO already exist. Immediately after, take however much #2 you need to keep working on overlays — since the Android VM is under @Suppress("TooManyFunctions"), the overlay stack has a forcing function now.

Bundle note: every candidate leaves overlapping tests intact; no ADRs exist that would forbid any of them; the corpus has no GLOSSARY.md — after the owner picks, I'd add a GLOSSARY file as a follow-up that captures any new name (e.g. "Date vocabulary" or "Overlay stack") realized by their chosen candidate.
