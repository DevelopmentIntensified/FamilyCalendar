# 196 — Migrate sessions from lucia (archived, EOL) to Better Auth

Status: in-progress

Source: owner question 2026-10-16 ("are we still using lucia? why haven't we moved to betterauth?") + #161 finding (`lucia@3.2.2` archived upstream, no CVE, zero maintenance). Lucia's author's successor project is Better Auth. **Design decided 2026-10-16 — ADR-0002 governs** (self-hosted Better Auth 1.7.x on Neon; sliding 90d sessions; bcrypt custom verify; placeholder-email guests; codes table replaced wholesale; normalization ours; throttle policy table; MFA deferred).

## Done

- **Slice 5 (bcrypt decision + credential parity, 2026-10-21):** DECISION — **keep bcryptjs**; no hash re-wrap, no forced resets. Concretely: `login/password` keeps verifying `users.passwordHash` via `verifyPassword` (bcryptjs, `src/lib/server/utils/password.ts`); migration 018 backfilled `auth_account.password` from `users.passwordhash` for existing users; and the missing WRITER is now fixed — `createUser` (db/actions/users.ts) atomically writes the user row AND the better-auth `auth_account` credential row (`id='pw-'+userId`, `providerId='credential'`, `accountId=userId`, same bcrypt hash — mirroring 018's backfill shape exactly) whenever `passwordHash` is present, so post-cutover signups are visible to better-auth's model without re-running 018. Users without a password (guests, OAuth/email-code users) get no credential account row. Covered by `users.test.ts` (transaction write-order + guest case). When slice B wires better-auth's API surface, bcrypt stays the hashing currency via config — never a re-wrap.

- **Slice 0 (prep, 190f8a4):** row-id generation decoupled from lucia — `src/lib/server/utils/generateId.ts` (byte-identical alphabet/lengths to lucia's generator); `schema.ts` + 6 actions/routes re-pointed; remaining lucia imports = auth.ts (slice 1) + 5 TimeSpan/oslo sites (slice B). ADR-0002 written.
- **Slice 1 (session cutover, dd2412c):** `auth.ts` moved to better-auth behind the same interface; anon invariant concentrated; migration 018; typed check 0 errors. Follow-up fixed 2026-10-19: `auth.test.ts` shipped with an unhandled rejection (inner-scoped env swap could never apply to the cached `SESSION_SECRET`) — tests now load a fresh module instance per secret (`vi.resetModules()`), matching the per-process scheme.
- Ground truth (slice-2 recon 2026-10-21): slices 0/1 landed more than the Done notes said — schema.ts already has the three better-auth tables matching 018 byte-for-byte, hooks/login/signup/claim/forgot-password/email-change/account-deletion call sites are cutover (zero source imports of `lucia`/`@lucia-auth` left), and 018 already keeps bcryptjs (login verifies `users.passwordHash`; 018 backfills `auth_account.password` from it). Crisp gaps found and killed in slice 2:
  - **Migration bundle drift (the real bug, #050's failure class):** `db/migrations/scripts.ts` stopped at 016 — `016-drop-user-ad-consent`, `017_create_child_consent_records` (190) and `018_better_auth_tables` were never bundled, so the cold-start runner would NEVER create the better-auth tables on deployed envs. Fixed + `scripts.test.ts` parity gate added: every file in `sql/migrations/` must be bundled byte-identically, sorted — the omission class is now impossible to miss silently.
  - **`auth_account` had no writer** (only the 018 backfill): new signups got `users.passwordHash` but no credential account row. Fixed in slice 5 — `createNewUser` writes both in one transaction.

- Trivial couplings, easily swapped: `generateId` from `'lucia'` (8 files) and `TimeSpan` (5 files). `oslo/jwt` (magic link, password reset, email-change binding) is pilcrow's separate library — not lucia — and can stay or ride along (see risks).
- Why no move happened so far: no recorded decision anywhere in docs; the Oct hardening lane (contact/claim/password/email-change throttles, code binding to consumers) worked beside lucia, not through it.
- What the move buys: a maintained upstream; MFA/2FA + passkeys + session-manager/recovery plugins out of the box (directly closes audit #176 MFA-absent and much of #169 token/session hygiene); managed option exists on Neon (`neon-auth`, Managed Better Auth) — same DB, one credential.

## Needs doing

  1. Decide self-hosted Better Auth (pkg + Neon tables) vs Neon managed (`neon-auth`). Managed is the boring default unless integration blocks; verify Neon plan supports it.
  2. Schema swap: better-auth's `user`/`session`/`account` tables per its drizzle adapter; lucia `sessions` rows carry no user data (sessions only) so historical session records can be dropped, NOT migrated — migration SQL hand-run per repo rule (sql/ + issue note, never rely only on drizzle-kit push).
  3. Call sites: `auth.ts`, hooks server validation, login/signup/claim/create-account/forgot-password/email-change/account deletion (`users.ts:53-65` deletes sessions/ subscriptions — update to better-auth's session path), cookie cutover invalidates ALL live sessions (pre-prod acceptable; note in deploy).
  4. The Oct hardening MUST survive verbatim: per-client-key rate limits (contact/claim/password/email-change), email codes bound to consumers, claim-request privacy. These live in repo code + `codes` table, not lucia — port, don't lose: each hardened path gets its existing tests re-run green after the move.
  5. Email uniqueness/password hash format: `users.passwordHash` (bcryptjs) — better-auth password account needs its own `account` table + hashing; write a one-time hash re-wrap on first login or keep bcryptjs via plugin config — decide in the ticket, prefer keeping bcryptjs hashing (crypto-agnostic to better-auth) to avoid forced password resets.
  6. `generateId`/`TimeSpan` decoupled first as a zero-risk prep commit so blocking on the migration is not needed (half-migration of lucia itself is NOT acceptable — either lucia stays fully in place or it goes).

- Out of scope: any marketing-auth surface other than what exists; no new providers.

## Risks

- Lucia is EOL: a real session/auth bug stays unfixed forever — this is the durable argument for the move, not the CVE board (nothing currently flagged against lucia itself).
- Migration touches login for every user + DB schema — go slow, separate commits per step 1–7, manual SQL for the user to run, verified on the test deploy before prod.
