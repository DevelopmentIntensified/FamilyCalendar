# dayDashboard

**screen** — The Day Dashboard: composes events, Top-3 Priorities, Family Task Board, Kids Schedule, groceries, for one viewed day.

Domain words come from [CONTEXT.md](../../../../CONTEXT.md); use them exactly. Architecture rules: [docs/architecture/rules.md](../../../../docs/architecture/rules.md).

## Purpose

- Owns the `/calendar/dashboard` page and its `/api/dashboard` twin: ONE composition of the viewed day (events, Top-3 Priorities, Family Task Board, Kids' Schedule, Groceries, Completed Today) so the page and the Android app cannot disagree.
- Owns the card band: which Dashboard Module renders where (info band vs cards), the two-group/one-grid layout, the skeleton that holds the band's shape while data streams, and the "Couldn't load … just now" banner.
- Owns the card-level presentation rules: glance rows (all-day first, one line each) and the Kids' Schedule grouping per child.
- Does not own: any read it composes. Day events and attendance are calendar's; Top-3 ranking, the Family Task Board list, day completions and the streak are tasks'; visibility is dashboardModules'; the roster is family's; the zone and settings are identity's; groceries is its own module. The verse feature is gone (2026-11-12); its Dashboard Module id stays. The event edit sheet is calendar's UI; the screen only opens it.
- Does not own: Meals (parked). No tables, no repo — a screen composes domain services through their `index.server.ts`.

## Public interface

Designed before the code (S1). The deletion test is stated per export: if deleting it only moves its body into the caller, it does not belong here.

- `index.ts`
  - `DashboardModel` — the resolved `/api/dashboard` body: `{ zone, dayISO, isToday, meId, familyId, modules, taskCategories, data, warnings }`, where `data` is `DashboardData`. Cards type their props from it (`DashboardModel['data']['kidsSchedule']`), so no card owns a second wire shape (architecture review 2026-11-10 #3). Deleting it would force every card to re-declare the shape the golden pins.
  - `DashboardData` — the ten streamed legs (`userTasks`, `familyTasks`, `familyMembers`, `dayEvents`, `top3`, `glance`, `completedToday`, `kidsSchedule`, `familyGroceries`, `mineGroceries`), each leg's wire row schema living in `dayDashboard.contract.ts` and built field for field from the golden. Not a copy of a legacy type: a field is added here only when the golden adds it, and the two task legs are separate schemas because their legacy reads select different columns.
  - `DashboardPageData` — `Omit<DashboardModel, 'data' | 'warnings'> & { data: Promise<DashboardLoadedData>; loadWarnings: string[] }`: what the page load returns while the band streams. One derivation of the model, so the page cannot drift from the API; `DashboardLoadedData` is the ten legs plus the legs' own labels (the API strips those into `warnings`).
  - `DayDashboardPageData` — the page's own payload: `DashboardPageData` plus `defaultView` (the one header-only fact the Back-to-Calendar link needs).
- `index.server.ts`
  - `loadDayDashboard` — the ONE composition (`(ctx, actor, { date, categoriesP?, familyMembers? })`): zone and day window from identity, the one `dashboardVisibility` answer, then the ten legs through the domains' entries (tasks' list/board/ranking/day completions/streak/categories, calendar's ranged day read + attendance, family's membership/roster, groceries' two lists). Each leg degrades to its fallback and label; no visible module's read is issued for nothing.
  - `loadDayDashboardPage` — the page's `load` (`pageLoad({ auth: 'user' })`, 302 `/login`): starts the category read before `parent()`, hands the layout's roster to the service and adds `defaultView` to the payload.
  - `getDayDashboard` — `GET /api/dashboard` as an `endpoint()`: same composition, awaits `data`, strips the legs' labels and merges `loadWarnings` then the legs' labels.
- `ui/index.ts`
  - `DayDashboardPage` — the whole page body (document title, day header + DayNav URLs, warning banner, streamed card band, the event sheet). One export because the route renders one component; the band and the six cards are composition detail and stay internal (deleting an export that no screen or route may import fails the deletion test).
- `dayDashboard.state.svelte.ts` (module root, not an entry export): `DayDashboardState` — the cards' three writes (quick-add, complete toggle with the recurring Undo, priority) with injected api/toasts/refresh, tested in node.

Module-internal (not entry exports; the cards and this screen's S5/S6 composition import them directly): `dayDashboard.contract.ts` — `DASHBOARD_INVALID_DATE`, `DashboardDayQuery`, and the `DashboardModel` / `DashboardData` schemas with their row schemas; `dayDashboard.cards.rules.ts` — `orderGlanceEvents`, `groupKidsSchedule`, `initialsFromName` and their row types.

## How to test

- Whole module: `npm run test:mod -- dayDashboard` (add `--legacy` while the legacy dashboard tests remain).
- HTTP contract: `dayDashboard.http.db.test.ts` — committed mode (`beforeEach(truncateAll)`), real Postgres (`docker start familycalendar-db`), the ROUTE module imported by relative path. Verification runs with `TZ=UTC` (production parity), because two Task fields reach the wire as the driver's Postgres render rather than ISO. Covers 401, every 400 wording, the full 200 body, absent `?date=`, an impossible date, the viewer-zone read, and the module-skip case. There is no 403/404/409/429 branch on this route, so there is no golden for them.
- Contract (S3): `dayDashboard.contract.test.ts` — parse tables for the `?date=` query (the regex, the impossible date it lets through) and for the resolved payload; no setup.
- Pure screen rules (S3): `dayDashboard.cards.rules.test.ts` — tables for glance ordering and Kids' Schedule grouping, no setup.
- Service (S5): `dayDashboard.service.db.test.ts` — `rollbackTest` + `goldenCtx({ now })`: the full family day (every leg), the skip matrix, the stored-zone day window and the impossible-date/today fallback. A per-leg FAILURE cannot be forced without a mock (R9: one db serves every read), so the labels' order is pinned by the code path and the golden's empty list; listed in the sheet's Notes.
- UI (S7): `ui/*.svelte.test.ts` with props only; `dayDashboard.state.test.ts` (module root) in node with a fake api and memory toasts (no DOM, no fetch).
- No fixtures file: the service tests seed through the kernel's `seedUser` and the kernel tables, as the golden does.
