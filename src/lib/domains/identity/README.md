# identity

**domain** — Users, sessions and session cookies, personal API tokens (fp_), user settings incl. time zone, Anonymous Account detection, email codes, password hashing.

Domain words come from [CONTEXT.md](../../../../CONTEXT.md); use them exactly. Architecture rules: [docs/architecture/rules.md](../../../../docs/architecture/rules.md).

## Purpose

- Owns: the person row (`users`), the session row and the signed session cookie, personal `fp_` API tokens, calendar settings (incl. the user's stored time zone), Anonymous Account detection, hashed email codes and password hashing.
- Owns the `/api/me/api-tokens`, `/api/me/profile`, `/api/me/settings` and `/api/me/sessions/revoke-others` endpoints — the person's own data, never another person's.
- Does not own: sign-in, sign-up, Magic Link, Claiming, Claim Conflict and email-change flows ([access sheet](../../../../docs/rewrite/modules/access.md)); subscription data and plan limits ([billing sheet](../../../../docs/rewrite/modules/billing.md)); notification preferences ([alerts sheet](../../../../docs/rewrite/modules/alerts.md)); the `/api/me` shell (`familyId`, roles for the app chrome) — that composition belongs to the account screen.

## Public interface

Designed at S1 and implemented by S5+S6; each entry hides a whole use-case, so callers never re-implement a rule. The deletion test keeps it small: merging a settings patch, signing/verifying a cookie, deciding a renewal, hashing and scoping a token, binding an email code and clearing a default calendar are all behaviour that would otherwise be copied into `app`, `access` and `account`.

- `index.ts`:
  - `isAnonymousAccount(user)` / `isRegisteredAccount(user)` — the ONE Anonymous Account predicate (placeholder `@anonymous.placeholder.invalid`); "registered" is a real email, never `user.email` truthiness.
  - `displayName(person)` — `firstName lastName` trimmed, the single person-label rule.
  - `guestSafeEmail(user)` — the placeholder email leaves the server as `null`; every wire that carries a person uses this. (Designed as `maskEmail`; renamed at S3 because family's search rules export a different `maskEmail(email)` — partial masking — and R11 needs unique names.)
  - `ACCOUNT_SETTINGS_DEFAULTS`, `calendarSettingsPatch(body)` — the settings wire vocabulary, allowlist and defaults, pure. The no-row builder (`newCalendarSettings`) is internal: only the settings service's insert path needs it.
  - `sessionCookieAttributes(production)` — the cookie attribute policy, pure. The lifetime constant, the 24-hour renewal window and the renewal/expiry math stay internal to `identity.session.rules.ts`: no caller needs them, and the session service owns the decision.
  - `apiTokenName(raw)` — cut at 60 code points, then trimmed (`fp_` minting is server code).
- `index.server.ts`:
  - `CalendarAccessPort` — `{ listAccessibleCalendarIds(userId): Promise<readonly string[]> }`, implemented by calendar; identity calls it through `ctx` to validate a new default calendar.
  - `AdConsentPort` — `{ listConsentHistory(userId): Promise<readonly ConsentRecordView[]>; recordConsentChange(userId, previous, next): Promise<void> }`, implemented by sponsored; identity calls it through `ctx` for the settings view and the ad transition.
  - `IdentityPorts` (`{ calendarAccess, adConsent }`) and `IdentityCtx = Ctx & IdentityPorts` — the ctx the settings service takes (the family precedent; declared at S3, wired once in `src/lib/app/ports.server.ts`).
  - `resolveCodePepper(secret, production)` — the fail-closed `EMAILSECRET` email-code pepper (production without it refuses to boot; `CODE_PEPPER_PLACEHOLDER` elsewhere), read once by `src/lib/app` into `ctx.config.codePepper` (Q-117).
  - `PersonView` — the person shape every entry answers: id, names, the guest-safe email, `emailVerified`, `isAnonymous`, roles, `lastActiveAt` (a type, not a wire schema: no identity `/api` route answers a person).
  - `getPerson(ctx, actor)` — the caller's own person (no other id is accepted): names, email masked, `emailVerified`, `isAnonymous`, `roles`, `lastActiveAt`.
  - `getPersonByEmail(ctx, email)` / `isEmailTaken(ctx, email)` — the exact-match read and the sign-up/child-door guard (`users.email` is unique). Both read only identity's table; family calls them instead of importing the repo.
  - `getPersonById(ctx, personId)` — the raw row by id (placeholder email included), a miss is `null`; access' account flows read the caller this way after their own proof (a code, a signed token, a session).
  - `verifyPersonEmail(ctx, personId)` / `setPersonEmail(ctx, actor, {email})` / `setPersonPassword(ctx, personId, {password})` — the three writes access composes: flip `emailVerified` for the redeemed code's person, apply a verified email change on the caller's own row, and replace `users.passwordHash` (only that column, Q-104) after the reset token proved the person.
  - `createPersonWithPassword(ctx, input)` — one transaction: the `users` row, plus `users.passwordHash` AND the `auth_account` credential row (`pw-<userId>`, `providerId:'credential'`) when a password is given. Without a password it writes only the user row, which is the child door's real, passwordless account (legacy `createUser`).
  - `createEmailPerson(ctx, {email, firstName, lastName})` — the magic-link/Android sign-up person (legacy `createNewUser`): a verified `users` row, its `email` provider binding and a random-colour settings row in ONE transaction. The personal calendar is the caller's composition (calendar creates it lazily).
  - `findPersonForSignIn(ctx, email)` — `{bound, person}`: the `email` provider binding first (`getAccount` → `getUser`, the mobile/callback order), the `users` row by address only when there is no binding; a binding whose person row is gone answers `{bound:true, person:null}` instead of falling back.
  - `ensurePersonSettings(ctx, userId)` — the sparse `timeZone:'UTC'` settings row when none exists (the Android password door and the Claim backfill). Idempotent.
  - `updatePersonProfile(ctx, actor, input)` — trims and writes `firstName`/`lastName` only; privilege fields cannot pass through.
  - `createAnonymousAccount(ctx)` — one row with a placeholder email plus `timeZone:'UTC'` settings; the "document navigation only" gate stays in `app` hooks.
  - `touchLastActive(ctx, actor)` — the Inactivity Window input, at most once per hour.
  - `listPersonNames(ctx, ids)` — the stored `{id, firstName, lastName}` of an id set (tasks' stats assigner/assignee/done-by figures and its assignee/creator fields); unknown ids are absent, the order is not claimed, and `personFullName` is the one untrimmed full-name formatter (`'Sam '`, the legacy SQL shape).
  - `getTimeZone(ctx, userId)` — the stored zone as Luxon resolves it (`setZone(...).isValid`, so `UTC`/`America/Chicago` and also the pseudo-zones `local`/`system`/`UTC+5`), `undefined` = server-local.
  - `startSession(ctx, userId)` / `validateSession(ctx, cookieValue)` / `resolveSessionCookie(ctx, cookieValue)` / `endSession(ctx, sessionId)` / `endAllSessions(ctx, userId)` / `endOtherSessions(ctx, actor, { keepSessionId })` — session CRUD, cookie signing/verification (`token.hmacSHA256(token)`, raw, never re-encoded), sliding renewal, "log out everywhere" (the `userId` access's password reset holds), the "keep mine" logout. `keepSessionId` is explicit: the http layer passes `event.locals.session?.id ?? null`, so a Bearer caller (no session) keeps none. `startSession` answers the stored row and its cookie; `resolveSessionCookie` is the session pipeline's whole cookie path — the signed-in person, the cookie to write back (the rolled one when fresh, the blank one when the value died, null when nothing changed) and the hourly `lastActiveAt` touch. `sessionCookie(ctx, token)` re-issues a cookie on a fresh roll and `blankSessionCookie(ctx)` clears a dead one. The signing secret and production flag come from `ctx.config`; `resolveSessionSecret(secret, production)` is the fail-closed rule `src/lib/app` calls once at boot.
  - `listApiTokens(ctx, actor)` / `mintApiToken(ctx, actor, {name})` / `revokeApiToken(ctx, actor, id)` / `revokeAllApiTokens(ctx, userId)` / `revokeApiTokenByPlaintext(ctx, userId, plaintext)` / `authenticateApiToken(ctx, token)` / `resolveBearer(ctx, authorization)` — personal tokens (`fp_` + 32 random bytes base64url); plaintext only from mint, hash never leaves, revoke owner-scoped. `revokeAllApiTokens` and `revokeApiTokenByPlaintext` take the `userId` the caller already holds, not an actor: password reset (a verified reset token, no session) and mobile logout call them that way; `revokeAllApiTokens` takes the caller's own token too, `revokeApiTokenByPlaintext` exactly the presented one. Authenticate resolves the owner and touches `lastUsedAt` (a write, so not named `get…`); `resolveBearer(ctx, authorization)` is the pipeline's decision on top of it — `none` (no Bearer header, keep going to the cookie), `invalid` (answer 401 and never resolve) or `person` — and it knows nothing about paths, because only the caller may decide where a token is accepted. `isApiTokenFormat(token)` is exported beside them for access' mobile logout, which must refuse a non-`fp_` bearer with the same 401 the legacy handler did.
  - `getCalendarSettings(ctx, actor)` / `updateCalendarSettings(ctx, actor, patch)` — the merged settings view, default-calendar access check (through `ctx.calendarAccess`), consent transition (through `ctx.adConsent`); validates the same values the legacy route validates.
  - `setHiddenDashboardModules(ctx, actor, hidden)` — the Dashboard Module switches' own save (#105): creates the row with the page defaults plus the hidden list when none exists, otherwise writes only that column. `PATCH /api/me/settings` keeps refusing `hiddenDashboardModules` as an unknown field, as its golden pins.
  - `hashPassword(password)` / `verifyPassword(password, hash)` — bcrypt cost 10.
  - `findEmailCode(ctx, {code, email, type})` — the same keyed lookup as redeem, WITHOUT consuming: the reset marker's second-use check and the email-change token's pre-flight need a hit that leaves the row in place.
  - `discardEmailCodes(ctx, email, type?)` — every code bound to one address, or only those of one `type` (access's email-change request replaces its own kind, so the reset marker survives).
  - `issueEmailCode(ctx, input)` / `redeemEmailCode(ctx, input)` — every kind stores `HMAC-SHA-256(ctx.config.codePepper, code)` (`emailCodeKey`, Q-117), the `email_change` code and the `reset_used` marker included (Q-116), and every lookup binds email AND type. A redeem consumes the row and answers it, or answers `null` for a miss, a wrong code, an expired row or a mismatched email/type; the flow that owns the refusal supplies its copy.
  - `deletePerson(ctx, actor)` — deletes the users row; sessions, settings and tokens cascade. It knows nothing about other modules' rows: the caller (the account screen's deletion composition) clears them (see Invariants).
  - Endpoint handlers: `listApiTokensEndpoint`, `createApiTokenEndpoint`, `revokeApiTokenEndpoint`, `updateProfileEndpoint`, `revokeOtherSessionsEndpoint`, `getSettingsEndpoint`, `patchSettingsEndpoint`.
- `ui/index.ts`: nothing — identity owns no component (S7: none). The account screen's `ui/Account*Section.svelte` components render the profile, calendar-settings, security and API-token sections from its own service calls.
- Deleted legacy exports (deletion test): `getCodes`, `getCodesByEmail`, `getAccounts`, `updateAccount`, `deleteAccount` (the `accounts` action), `deleteUserByEmail` — no importers, and the new repos name the queries they need.

Module-internal, exported from no entry file (each tested by the `*.test.ts` next to its stem): the rest of the five rules files — `isIanaTimeZone`, `newCalendarSettings`, `defaultCalendarToCheck`, `calendarSettingsView`, `writableSettings` and the settings vocabularies; `anonymousPersonValues`, `profilePatch`, `touchDue`, `zoneFromStored`; the session lifetime/renewal math, the signed-value split and the Set-Cookie header; `apiTokenPlaintext`, `isApiTokenFormat`; the email-code kinds, TTL and `emailCodeKey` — and the whole repo. The services are their only callers.

**Cross-module ports ride on `ctx`, never on a route file** (the [add-a-port](../../../../docs/rewrite/playbooks/add-a-port.md) seam). Identity declares the two interfaces above; calendar and sponsored implement them; `src/lib/app/appCtx.server.ts` — the only place allowed to import every module — builds them into the production `Ctx`. Tests get the REAL adapters through `goldenCtx` from `$lib/app/testing/goldenCtx.server` (kernel, K-12) — a golden may never see a stub, so a port cannot be "made green" by a fake; S5 service tests use `testCtx`'s in-memory fakes. Services read `ctx.calendarAccess` / `ctx.adConsent`; endpoints and `+server.ts` files never compose a port, so `/api/me/settings` stays `export const PATCH = patchSettingsEndpoint.handler`. Identity keeps `Reads: none / Calls: none` (R1/R3): it never imports `calendars`, `familyMembers` or `adConsentRecords`.

Deferred access primitive: the password-reset "revoke every session and token" rule is access's use-case built on identity's public `endAllSessions` and `revokeAllApiTokens`; its test lands with access.

## How to test

- Whole module: `npm run test:mod -- identity` (its seven legacy test files were deleted at S8; the new rules/repo/service/http tests replace them).
