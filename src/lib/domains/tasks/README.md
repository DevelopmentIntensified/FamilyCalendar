# tasks

**domain** — Tasks: visibility, priority, assignment handoff, Recurring Task cursor, tags, categories, completions, stats/streaks, archive, TaskFocus focus time + phone sessions, task UI.

Domain words come from [CONTEXT.md](../../../../CONTEXT.md); use them exactly. Architecture rules: [docs/architecture/rules.md](../../../../docs/architecture/rules.md).

## Purpose

- Owns the **Task**: creation, edits, deletion/archiving, the **Task Visibility** rule, the assignment handoff (**Requested / To Accept**), Task Priority, tags, per-user categories, and **completion history**.
- Owns the **Recurring Task** cursor (one live occurrence, skip and undo), the overdue pin that runs before reads, and the completion counts stats and the weekly streak are built from.
- Owns TaskFocus: the desktop focus fields (`focusMinutes`, `focusStartedAt`), the phone focus sessions and their absorb ack, and the per-user device command FIFO.
- Owns the task UI: the `/calendar/tasks` page state and components, plus the Task pieces other screens embed (the event checklist).
- Does not own: Events and calendars (calendar — a Task may attach to an Event and is filtered by its calendar), the Alert feed storage and push fan-out (alerts — tasks only asks it to notify), Family membership and the roster (family), quick-add grammar and date vocabulary (parsing), Task rendering inside the Day Dashboard cards (dayDashboard composes this module), plan retention for the archive page (billing/calendar).

## Public interface

Everything other modules and routes may use, grouped by entry file. One line each: `name` — what it does. Every server use-case takes `(ctx, actor, …)`: the actor is explicit, never read from the ambient request, and an input object rides last when one is needed.

- `index.ts`:
  - `TaskWire`, `TaskWithTagsWire`, `TaskCategoryWire`, `FocusCommandWire`, `FocusSessionWire` — the `/api` shapes (absent-vs-null documented per field).
  - `TaskCreateBody`, `TaskUpdateBody`, `TaskCategoryNameBody`, `FocusCommandBody`, `FocusSessionStartBody`, `FocusSessionEndBody` — zod schemas for every request body, with the legacy error wording.
  - `normalizeTags`, `normalizeTaskVisibility` — the tag and visibility rules.
  - `normalizeTaskPriority` — returns parsing's `QuickAddPriority` (the quick-add result's own type; the tone map stays with the pill in `kernel/ui`), so a Task's priority and a parsed title's priority are ONE concept.
  - the recurrence frequency has NO home here: it is kernel/time's `RecurrenceFrequency` (`scheduleStep`'s closed set), the one type calendar and parsing use too — a Task's `recurrenceFrequency`, an Event's and a parsed cadence are one vocabulary.
  - `nextCursorDue` — the Recurring Task cursor advance (today + n×interval strictly past the current due), used by the completion, skip and undo. The pin (`needsOverduePin`, `pinnedDueFor`) stays inside the module: it is a read-side service concern, not an interface other modules call.
  - `canMutateTask`, `nextAssignmentPatch` — the two rules that decide what a caller may do to a Task and how an assignment moves (pure; membership arrives as a flag).
  - `computeWeeklyStreak` — the one streak definition, shared with the Day Dashboard (`isoWeekKey` and the cursor's day-start helper live in `kernel/time`, task K-06, with every other date key).
  - `rankTasks` — mine-first → priority → overdue → due-today → next-due → title (Top-3 Priorities and the Family Task Board order through it).
  - `createTasksApi` — typed browser client for this module's endpoints (kernel api client); no UI state.
- `index.server.ts`:
  - `unassignMemberTasks(ctx, familyId, userId)` — the `family` `MemberTasksPort`: clears a removed member's Family Task assignments (`assignedTo`/`assignmentStatus`), writing through the caller's `ctx.db` so it joins family's removal transaction.
  - `listTasks(ctx, actor, { eventId? })` — one read, one list shape (Q-055). The main leg pins stale cursors, attaches tags, `eventCalendarId` and the phone-focus overlay; the `eventId` leg answers the same shape for the Event's rows and does NOT run the pin. Both legs apply the private read rule (owner or, while assigned, assignee — Q-005a).
  - `listTaskSections(ctx, actor)` — the three queues (my Tasks, To Accept, Requested) and the per-leg `warnings` labels. It pins cursors through the same `listTasks` leg first (`tasksData.ts:37`), which is why a section row can already carry today's pinned due.
  - `listFamilyTasks(ctx, actor, { familyId })` — the Family Task Board read: the family's Task rows plus the members' Public Tasks, with the public tab's own visibility filter and the member-personal pin leg; familyHub's `GET /api/families/{id}/tasks` composes this with the roster and the viewer's categories.
  - `createTask(ctx, actor, body)`, `updateTask(ctx, actor, { taskId, body })` (undo → skip → toggle → patch dispatch), `deleteTask(ctx, actor, { taskId })`, `clearCompletedTasks(ctx, actor)` — the mutation use-cases, including event/family/assignee authorization, category auto-add and the assignment/completion Alerts.
  - `listTaskCategories(ctx, actor)`, `addTaskCategory(ctx, actor, { name })`, `renameTaskCategory(ctx, actor, { categoryId, name })`, `removeTaskCategory(ctx, actor, { categoryId })` — the per-user category list with its propagation rules.
  - `listFocusCommands(ctx, actor)`, `issueFocusCommand(ctx, actor, { command, taskId })`, `ackFocusCommand(ctx, actor, id)` — the per-user device command FIFO.
  - `startFocusSession(ctx, actor, { taskId, startedAt, endedAt })`, `endFocusSession(ctx, actor, { id, endedAt })`, `discardFocusSession(ctx, actor, id)`, `absorbFocusSession(ctx, actor, id)`, `listUnabsorbedFocusSessions(ctx, actor)` — phone focus sessions; every call scoped to the caller. The session time rules (`sessionTimesError`) and the overlay math (`summarizePhoneFocus`/`getPhoneFocusOverlay`) stay internal; the wire only carries their result.
  - `getTaskStats(ctx, actor)`, `listCompletionInstants(ctx, actor)`, `getStatsPage(ctx, actor)` — the counting path (shared with the dashboard) and the `/api/stats` body.
  - `resolveTaskQuickAdd(ctx, actor, { text, dueDateFallback?, visibilityFallback?, category? })` — parsing's grammar resolved into a contract-parsed `POST /api/tasks` body (`{ title, body }`); it never writes a Task. The S7 quick-add component creates through the one `createTask` use-case.
  - Endpoint handlers, one per `/api` route+method: `listTasksEndpoint`, `createTaskEndpoint`, `updateTaskEndpoint`, `deleteTaskEndpoint`, `clearCompletedTasksEndpoint`, `taskSectionsEndpoint`, `listTaskCategoriesEndpoint`, `createTaskCategoryEndpoint`, `renameTaskCategoryEndpoint`, `deleteTaskCategoryEndpoint`, `listFocusCommandsEndpoint`, `issueFocusCommandEndpoint`, `ackFocusCommandEndpoint`, `listFocusSessionsEndpoint`, `startFocusSessionEndpoint`, `endFocusSessionEndpoint`, `discardFocusSessionEndpoint`, `absorbFocusSessionEndpoint`, `taskStatsEndpoint`. The route files re-export them as `handler` (R8).
- `index.ts` (browser half, added S7): `createTasksApi`/`TasksApi` — the typed endpoint client; `TasksPageState`, `TaskQuickAddState`, `EventTaskChecklistState` — the page's state classes (`TasksStateOptions`, `TaskQuickAddOptions`, `TaskChecklistOptions`, `FOCUS_SETTLE_MS`); `TaskPageRow`/`TaskPageData`/`TaskSections`/`TaskCategoryItem`/`TaskRosterMember` — the load shapes the components type on; the list/display/editor/quick-add rules and their types (`TASK_CHIPS`, `TASK_OWNER_VIEWS`, `TASK_SORT_KEYS`, `TASK_TIME_FILTERS`, `matchesTask*`, `sortTaskRows`, `taskBucketCounts`, `taskLateChip`, `taskMemberName`, `taskRowFromWire`, `taskUrgencyBucket`, `taskMetaSlots`, `taskRecurringCompleteText`, `taskRecurringSkipText`, `buildTaskEditPayload`, `buildTaskQuickAddBody`, `splitTaskRecords`, `taskQuickAddRefusal`, …).
- `ui/index.ts`:
  - `TasksScreen` — the `/calendar/tasks` page body (builds the two state classes from the load data; mounts the kernel Toaster).
  - `TaskList`, `TaskRow`, `TaskDoneRow` — the list card (filter line, jump bar, one-off/recurring groups, tail states, clear-completed) and its two rows.
  - `TaskEditor` — the edit sheet (owner-only visibility, assignee picker, `buildTaskEditPayload`).
  - `TaskQuickAdd`, `TaskCategoryField` — the add card (live preview, bulk, smart templates) and the category picker it shares with the editor.
  - `TaskCategoryManager`, `TaskAssignments` — optimistic rename/delete and the two assignment queues.
  - `EventTaskChecklist` — the checklist the calendar page's event modal embeds (calendar CANNOT import tasks: it is rank 8, tasks rank 9; the calendarPage screen passes this component in as a snippet, rule R1).

Deletion test (why each export stays): `listTasks`, `listTaskSections` and `listFamilyTasks` are the one home for Task visibility, the cursor pin, tag attachment, event attribution and the phone overlay, so the seven legacy list readers (user list, event list, my Tasks, pending, requested, public tab, family board) cannot drift apart. `updateTask` swallows the 353-line route dispatch (undo, skip, toggle, five patch groups) so the dispatch order cannot drift from the rules. `canMutateTask`/`nextAssignmentPatch` are the one home for the rules that three routes and the UI repeat today. `nextCursorDue` is the cursor policy shared by the completion, skip and undo (the dive-into-the-DB half stays in the service). `computeWeeklyStreak` is the one streak definition the Day Dashboard and the stats page both read. `EventTaskChecklist` stays an export because it is the only way calendar's event modal can show a Task without importing this module.

## How to test

- Whole module: `npm run test:mod -- tasks` (add `--legacy` while legacy tests remain).
- Pure rules: `*.rules.test.ts`, plain tables of input → expected output, no setup.
- Database + services: `*.db.test.ts` using `rollbackTest` and `testCtx({ db })` (needs Postgres: `docker start familycalendar-db`).
- HTTP contract: `tasks.http.db.test.ts`, `tasks.update.http.db.test.ts`, `tasks.focus.http.db.test.ts` pin status + body of every endpoint (golden tests, committed mode). They were written against the legacy handlers and were not edited at S6; they now drive the ported endpoints through the same route files.
- Exact timestamp strings: `tasks.dueDate` / `completedAt` / `archivedAt` and `events.start` are `timestamptz` columns in drizzle `mode:'string'`, so the body carries the POSTGRES render (`2026-02-01 10:00:00+00`), not an ISO string; only `createdAt`/`focusStartedAt`/phone-session instants are `mode:'date'` and serialize as ISO. The `+00` suffix depends on the Postgres session `TimeZone`, which docker and production both pin to UTC — a session on another zone renders `+14` and every golden fails, which is the intended tripwire.
- UI state (node, unit project): `tasks.page.state.test.ts`, `tasks.quickadd.state.test.ts`, `tasks.checklist.state.test.ts` — fake api, `memoryToasts()`, a manual scheduler, a memory storage; no DOM, no `vi.mock` of app modules.
- UI rules: `tasks.list.rules.test.ts`, `tasks.display.rules.test.ts`, `tasks.editor.rules.test.ts`, `tasks.quickadd.rules.test.ts` — tables; the picker/paste splits and the toast copy are pinned here.
- Fixtures: `tasks.ui.fixtures.ts` (the client row/section builders) and `tasks.fixtures.server.ts` (row builders for this module's db tests; the only place a test creates task, tag, completion, category, command, session or user-zone rows).
