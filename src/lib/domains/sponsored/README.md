# sponsored

**domain** — Sponsored Events: the serve gate, the month's ads on the calendar, the consent trail beside it, and ad-row retention.

Domain words come from [CONTEXT.md](../../../../CONTEXT.md); use them exactly. Architecture rules: [docs/architecture/rules.md](../../../../docs/architecture/rules.md).

## Purpose

- Owns: the **Sponsored Event** decision — whether a user sees ads at all (`userSettings.showAdsAsEvents`, #088); the month's Sponsored Events (three generated ones, the sole source — [Q-040](../../../../docs/rewrite/questions.md) B); the consent trail (`adConsentRecords`) that records that decision's history; ad-row retention (`adEvents`).
- Does not own: the settings row itself (`identity` writes it; this module only reads the one field), the chip/legend look (`calendarPage` renders it from the row's `isAd` + amber), the opt-in checkbox and its consent-history display (the `account` screen). It reads no calendar table: a user's own 📢 Event is their calendar data, never ad inventory ([Q-040](../../../../docs/rewrite/questions.md) B).
- The one surface invariant this module is responsible for: every row it returns is marked `isAd: true` and amber, so no consumer can render a Sponsored Event unlabelled (`CONTEXT.md:40-42`).

## Public interface

Designed small and deep: a handful of exports carry the whole behaviour, and each survives the deletion test.

### `index.ts` (isomorphic)

- `shouldServeSponsoredEvents(settings)` — the ONE serve gate: `showAdsAsEvents === true`; no settings row, `null` and `false` all mean no Sponsored Events, and no other field can grant consent. Deletion test: inlining the comparison moves the one rule every ad surface depends on into each caller — the exact drift #088 exists to prevent; `calendarPage` also needs the same answer for its legend row, so it is a real interface, not a pass-through.
- `SPONSORED_EVENT_COLOR` — `#f59e0b`, the wire amber, defined in `sponsored.display.rules.ts` (the projection that writes it) so importing this entry never pulls the zod wire schemas into a browser bundle. Deletion test: the literal would otherwise live in the wire projection and in the chip recipe; #067 is the incident where those two drifted.
- Types: `SponsoredEvent` (the row the wire and the calendar render), `SponsoredConsentDecision`, `SponsoredEventsQuery`, `SponsoredEventsResponse` — the module's vocabulary, re-exported from the contract so callers never hand-mirror a wire shape.
- No client api (`sponsored.api.ts`): nothing in the browser fetches the route — the calendar gets its rows in the page load and Android is the only wire client. Adding one would be a pass-through.

### `index.server.ts`

- `listSponsoredEvents(ctx, actor, { month?, now })` — the month's Sponsored Events. Checks the gate FIRST (no ad read when off) through identity's `getCalendarSettings`, resolves the user's zone from that view, resolves the month (the validated `YYYY-MM`, or the month of `now` in that zone), draws the month's three generated rows from the `sha256(userId + 'YYYY-MM')` seed, and returns them carrying `isAd: true`, amber, `allDay: true`, no calendar and `created_at` = the month's start. Serves `GET /api/sponsored-events` and `calendarPage`'s ad leg. `now` is an input: the endpoint supplies `ctx.clock.now()` and the service tests pin one. Deletion test: the gate, the zone, the generation and the projection would each move into both callers.
- `recordSponsoredConsentChange(ctx, userId, { previous, next })` — appends one record on a real transition only (`granted` / `withdrawn`), returns the decision or `null`. It takes the person's id because identity's `AdConsentPort` hands it the already-authorized saver; inventing an `Actor` here would be a second, unverifiable authorization path. Deletion test: the transition rule is the whole point of the trail; a caller-side compare would fabricate "declined" rows for users who never touched the setting.
- `listSponsoredConsentHistory(ctx, userId)` — the person's whole trail, newest first. Deletion test: the read also promises "writes nothing"; a hand-written select forgets the order and invites a serve-log, which is what this table is deliberately not.
- `pruneSponsoredEventsOlderThan(ctx, cutoff)` — retention: deletes ad rows created before the cutoff, returns the count. Called by `app`'s weekly cron. Deletion test: the anchor (`createdAt`, not `scheduledFor`) is the rule.
- `sponsoredAdConsentPort(ctx)` — the real `AdConsentPort` identity declares (`listConsentHistory`, `recordConsentChange`), built from the ctx it is attached to and wired in `src/lib/app/ports.server.ts`. Deletion test: identity (rank 1) cannot import sponsored (rank 12), so without this adapter the consent trail would have no writer and no reader.
- The module declares no port of its own: the draw is seeded from `sha256(userId + 'YYYY-MM')` ([Q-041](../../../../docs/rewrite/questions.md) B), so it needs no `ctx` randomness.
- `listSponsoredEventsEndpoint` — the `GET /api/sponsored-events` handler (auth, month parsing, body). `+server.ts` stays wiring only.
- Deliberately absent: an engagement write (`trackAdImpression`/`trackAdClick` in legacy) and a target-plan reporting read. Neither is on the wire, neither has a consumer, and `adEvents` has no writer in v2 — they die with `injectAdEvent` and a future ad-inventory ticket designs them together (see the sheet Notes). The `adEvents` columns and the prune stay.

### `ui/index.ts`

Empty on purpose. Every sponsored surface is a screen's: the account checkbox and consent history (`account`), the chip word "Ad" / accessible name "Sponsored", the legend and the ad-less event modal (`calendarPage`). The dashboard's glance card keys on the same `isAd` flag if it is ever handed a sponsored row (today its loader passes calendar events only). Moving one here would split a visual recipe across two modules; this module's contribution is the `isAd` flag and the amber those surfaces key on.

### Module-internal

Exported from no entry file (S3+S4; the S5 service and S6 handler are their only callers): `SPONSORED_TITLE_MARKER` (`sponsored.display.rules.ts`); `sponsoredMonthOfKey(key)`, `sponsoredMonthKeyOf(month)`, `sponsoredMonthOf({ now, zone })`, `sponsoredMonthWindow({ month, zone })` → `{ fromIso, toIso }`, `sponsoredDrawSeed({ userId, month })`, `sponsoredSeededDraw(seedHex)`, `planSponsoredMonth({ month, zone, random })` → `{ message, start }[]`, `SPONSORED_EVENT_MESSAGES`, `SPONSORED_EVENTS_PER_MONTH` (`sponsored.month.rules.ts`); `toSponsoredEvent(source, { ownerId, createdAt })` (`sponsored.display.rules.ts`); `SPONSORED_CONSENT_DECISIONS`, `sponsoredConsentDecision(previous, next)` (`sponsored.consent.rules.ts`); and the repo's `insertSponsoredConsentRecord(db, { userId, decision, recordedAt })`, `listSponsoredConsentRecords(db, userId)`, `deleteAdEventsCreatedBefore(db, cutoff)`.

Randomness is a parameter and a function of the request: `planSponsoredMonth` takes a `SponsoredRandomSource` (a uniform draw in [0, 1)), so the rule stays pure and its tests script every draw; the service hands it `sponsoredSeededDraw(sponsoredDrawSeed({ userId, month }))`, i.e. `sha256(userId + 'YYYY-MM')` ([Q-041](../../../../docs/rewrite/questions.md) B), so the same user and month serve the same rows on every request. `created_at` is the month window's start ([Q-042](../../../../docs/rewrite/questions.md) B), computed by the service from `sponsoredMonthWindow`.

## How to test

- Whole module: `npm run test:mod -- sponsored` (add `--legacy` while the legacy tests remain).
- Pure rules: `*.rules.test.ts`, plain tables of input → expected output, no setup.
- Database + services: `*.db.test.ts` using `rollbackTest` and `testCtx({ db })` (needs Postgres: `docker start familycalendar-db`). `sponsored.service.db.test.ts` adds the two ports the settings view reads (identity's `calendarAccess`/`adConsent` fakes), gives the ctx the real `systemIds` so generated ids keep the legacy row-id shape, and pins every time with `testCtx({ now })` / the `now` input; the draw needs no fake, it comes from the seed the service derives (Q-041 B).
- HTTP contract: `sponsored.http.db.test.ts` pins status + body of `GET /api/sponsored-events` (golden tests, committed mode, `beforeEach(truncateAll)`). The S2 rows Q-040/Q-041/Q-042 B flip were changed with those answers; every other row is unchanged.
- Fixtures: `sponsored.fixtures.server.ts` (settings row for the gate, an `adEvents` row, a consent record).
- UI: no components here; the chip and legend are the calendar's tests, the checkbox the account's.

## Invariants

Each line is a behaviour the port must keep, with the legacy evidence and the test that pins it.

- The only serve gate is `userSettings.showAdsAsEvents === true`: a missing row, a `null` flag and a `false` flag all mean no Sponsored Events, and no other field on the row can grant consent — `src/lib/server/services/adService.ts:77-82`, `src/lib/server/services/calendarData.ts:84`. Pinned by `sponsored.http.db.test.ts` › "generates three Sponsored Events when the month has none", "withholds ads when the user has no settings row, even with 📢 rows in the month", "withholds ads when showAdsAsEvents is false", "withholds ads when showAdsAsEvents is null"; `sponsored.service.db.test.ts` › "withholds ads when the user has no settings row, even with 📢 rows in the month", "withholds ads unless showAdsAsEvents is exactly true"; and `sponsored.serve.rules.test.ts` (the one-row table, S3).
- Consent records are evidence, never permission: the gate never consults the trail (the settings view the serve path reads carries it, and `listSponsoredEvents` ignores it), and a serve read writes no record — `src/lib/server/services/adConsentService.ts:5-19`, `src/lib/server/db/schema.ts:917-933`. Pinned by `sponsored.http.db.test.ts` › "treats a consent record as evidence, never permission, and writes none on a read" and `sponsored.service.db.test.ts` › the same title.
- A consent record is appended only on a real transition: not-granted → true records `granted`, true → false records `withdrawn`, and an unchanged value (or a never-touched user saving with ads off) records nothing — `src/lib/server/services/adConsentService.ts:21-36`. Pinned by `sponsored.consent.rules.test.ts` (the four-row decision table, S3) and `sponsored.service.db.test.ts` › "appends only on a transition, stamped with the ctx clock" and "records nothing for a user who has never touched the setting".
- Records are append-only and read newest-first; a read never writes — `src/lib/server/services/adConsentService.ts:45-65`. Pinned by `sponsored.service.db.test.ts` › "keeps the whole trail newest first, and a read writes nothing"; the query by `sponsored.repo.db.test.ts` › "listSponsoredConsentRecords returns only the user's trail, newest first" and "insertSponsoredConsentRecord appends rather than replacing".
- A Sponsored Event month is a window in the user's zone: `startOf('month')` → `+1 month`, and the window's start is the served `created_at` — `src/lib/server/services/adService.ts:93-95`, `src/routes/api/sponsored-events/+server.ts:18`. Pinned by `sponsored.http.db.test.ts` › "windows the month in the user's zone, not UTC"; the window table (DST edges) by `sponsored.month.rules.test.ts`.
- An omitted `month` is the current month in the user's zone (settings zone, else UTC) — `src/routes/api/sponsored-events/+server.ts:17-27`. Pinned by `sponsored.http.db.test.ts` › "uses the current month in the user zone when month is absent".
- `month` is strict when present: `2026-13`, `2026-00`, `2026-1`, `nov`, `2026-11-01` and an empty value are all `400 {"error":"Invalid month"}` — `src/routes/api/sponsored-events/+server.ts:19-30`. Pinned by `sponsored.http.db.test.ts` › "answers 400 {"error":"Invalid month"} for month=…" and the `SponsoredEventsQuery` table in `sponsored.contract.test.ts`.
- The wire is `200 {"events": [<calendar display row> & {"isAd": true, "color": "#f59e0b"}]}`, `200 {"events": []}` when the gate is off, and `401 {"error":"Unauthorized"}` when signed out — `src/routes/api/sponsored-events/+server.ts:13-35`, `docs/guides/task-api-spec.md:531-539`. Pinned by the full-body and 401 goldens in `sponsored.http.db.test.ts`.
- The generated month is the sole source: a user's own 📢 Event is never served as ad inventory, and no calendar table is read — owner [Q-040](../../../../docs/rewrite/questions.md) B (`src/lib/server/services/adService.ts:97-123` was the legacy read). Pinned by `sponsored.http.db.test.ts` › "serves the requested month as calendar display rows marked isAd + amber, and never an own 📢 row", "draws the same month the same way on every request, and never the own 📢 rows", "does not serve an own event whose title starts with 📢, and generates the month instead"; `sponsored.service.db.test.ts` › "generates the month and never serves an own 📢 row (Q-040 B), the same draw on every read (Q-041 B)".
- Every served month carries exactly three Sponsored Events, at 10:00 in the user's zone on a day of that month, drawing templates without repeats while templates remain — `src/lib/server/services/adService.ts:126-183`. Pinned by `sponsored.http.db.test.ts` › "generates three Sponsored Events when the month has none"; the exact template/day table is `sponsored.month.rules.test.ts`; the service's seeded draw by `sponsored.service.db.test.ts` › "generates three Sponsored Events when the month has none".

Pinned by `sponsored.http.db.test.ts` › "draws the same month the same way on every request, and never the own 📢 rows"; the seed digests and the reproducible stream by `sponsored.month.rules.test.ts`; the service's repeat by `sponsored.service.db.test.ts` › the Q-040/Q-041 row.

Pinned by `sponsored.http.db.test.ts` › "generates three Sponsored Events when the month has none" (`/^[a-z0-9]{15}$/`, three distinct) and `sponsored.service.db.test.ts` › the same row, whose ctx carries the real `systemIds`.

Pinned by `sponsored.http.db.test.ts` › "uses the current month in the user zone when month is absent" and `sponsored.service.db.test.ts` › "uses the month of \"now\" in the user zone when month is absent".
- The display projection is fixed: `title` `📢 <message>`, `allDay: true`, `calendarId: ''`, `end` and `date` equal to `start`, amber `#f59e0b`, and `isAd: true` on every row; `created_at` is the served month's start, never the request instant (owner [Q-042](../../../../docs/rewrite/questions.md) B) — `src/lib/server/services/adService.ts:294-334`, `src/lib/server/services/calendarData.ts:60`, `src/routes/api/sponsored-events/+server.ts:35`. ## Depends on

- May import: kernel + identity, billing, alerts, family, dashboardModules, bills, parsing, calendar, tasks, groceries, verse (public entries only).
- Owns tables: `adEvents`, `adConsentRecords`.
- Reads: no other module's table. `FOREIGN_READS.sponsored.events` and the read it declared are gone with [Q-040](../../../../docs/rewrite/questions.md) B (the entry was deleted from `scripts/arch/registry.mjs` when this branch merged into `rewrite/v2`).

- Implements for `identity`: `AdConsentPort`, exported as `sponsoredAdConsentPort` and attached by `src/lib/app/ports.server.ts` (identity is rank 1 and never imports this module). The adapter is built from the ctx it is attached to, so it reads that request's database and clock.
- Declares no port of its own: the draw is seeded from `sha256(userId + 'YYYY-MM')` (Q-041 B), so `src/lib/app/ports.server.ts` wires no sponsored `random`.
- Called by: `calendarPage` (its ad leg: `listSponsoredEvents` for the visible month, `shouldServeSponsoredEvents` for the legend; the chip, legend and event-modal surfaces all key on `isAd`), the `account` screen (the opt-in checkbox and the consent-history list), `identity`'s `GET`/`PATCH /api/me/settings` (consent history read + transition write, through the `AdConsentPort` identity declares in its own `index.server.ts`), and `app`'s cleanup cron (`pruneSponsoredEventsOlderThan` at 90 days). Today the unported cron still calls the legacy `pruneAdEventsOlderThan`, because R8 forbids a non-wiring route importing module code; it switches when `app`'s cleanup is ported (see the sheet's S8 notes).
