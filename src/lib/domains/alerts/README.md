# alerts

**domain** — The Alert feed (closed type set, needs-you vs news), notification preferences, web push subscriptions, Android device tokens and push fan-out.

Domain words come from [CONTEXT.md](../../../../CONTEXT.md); use them exactly. Architecture rules: [docs/architecture/rules.md](../../../../docs/architecture/rules.md).

## Purpose

- Owns: the Alert feed — one row per Alert, the newest 50, the closed five-type vocabulary and the needs-you / news split — plus mark-read, mark-all-read and pruning; the four notification preference switches stored in `activeSubscriptions.notificationMethods`; Web Push (VAPID) subscriptions; Android FCM device tokens; and push fan-out (a visible Alert push and the silent `events_changed` nudge).
- Does not own: the Alerts page chrome, the bell's nav placement, or the account card markup (screens compose this module's `ui/` and `index.ts`); who can see a calendar — `calendar` resolves the `events_changed` audience and passes the user ids in; the `activeSubscriptions` row itself — `billing` owns it and this module reads/updates only its `notificationMethods` JSON through the declared foreign read; the FCM wire transport — `kernel` owns it (today's legacy `fcmService`).
- Alerts are created by other modules (`tasks` on assignment/completion, `family` on join) through `createAlert`; every Alert write is in-app and fires a push.

## How to test

- Whole module: `npm run test:mod -- alerts`.
- Pure rules: `*.rules.test.ts`, plain tables of input → expected output, no setup. The closed type set, group split, labels, chip counts, click rule and stored-preference parsing are all pinned here.
- Database + services: `*.db.test.ts` with `rollbackTest` and `testCtx({ db })` (needs Postgres: `docker start familycalendar-db`).
- HTTP contract: `alerts.http.db.test.ts` runs in committed mode (`beforeEach(truncateAll)`) and pins status + full body of every endpoint. The two `/api/me/notification-preferences` describes were spec goldens (their legacy route imported `accountData → sendEmail → $env/static/private`); the file still loads them dynamically, and since S6 the route is wiring to this module, so they run unedited. The public-key golden sets `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` before building `goldenCtx`, which is why that factory reads those env vars (Q-020: the answer is gated on both).
- Page load: `alerts.pages.http.db.test.ts` drives `alertsPageLoad` through `invokeLoad` (302 to `/login`, the feed + unread count, the unrecognised-type log line and its absence).
- Push never runs in tests: no `/api` route sends push, the service tests drive the channel seam with fakes, and `alerts.push.api.test.ts` drives the browser flow through a fake `PushEnvironment` + fake api. FCM and web-push are never contacted.
- Client state: `*.state.test.ts` run in node with a fake `Pick<AlertsApi, …>` and `memoryToasts()`, no DOM.
- UI: `ui/*.svelte.test.ts` render with props (`api`, `toasts`, `env`, `navigate`, `now`, `zone`); nothing is module-mocked and nothing fetches.
- Fixtures: `alerts.fixtures.server.ts` — `seedAlert`, `seedDeviceToken`, `seedPushSubscription`, `seedAlertPreferencesRow` (direct inserts, never through the services, so no push is sent).

## Invariants

Behaviour that must not change. Wire rules name the golden in `alerts.http.db.test.ts`; the rest name the test that pins them, with the step that adds it.

- The Alert vocabulary is exactly five types; the guard rejects non-strings, case variants and anything else — `alerts.vocabulary.rules.ts` — `alerts.vocabulary.rules.test.ts › is exactly the five-member union` (S3).
- Group is a property of the type: only `assignment_pending` and `assignment_declined` are **needs you**; every other type, including an unrecognised one, is **news** — `alerts.vocabulary.rules.ts` — `alerts.vocabulary.rules.test.ts › never lets an unrecognised type claim to need a decision` (S3), and the golden `GET /api/notifications › answers the caller feed newest first, guarded, with the unread count`.
- Labels are Asked you / Accepted / Declined / Completed / Added to family; an unknown type renders `Update` and never echoes the column — `alerts.vocabulary.rules.ts` — `alerts.vocabulary.rules.test.ts › labels an unrecognised type as Update rather than echoing the raw string` (S3).
- An unrecognised Alert is kept, never dropped: `type: null`, `rawType` preserved, group derived from the raw value, `link`/`readAt` normalised to null — `alerts.vocabulary.rules.ts` — same golden as above (the `mystery_type` row) plus `alerts.vocabulary.rules.test.ts` (S3).
- One feed, one page size: 50 rows, newest `createdAt` first, shared by the bell API and the Alerts page — `src/lib/server/db/actions/notifications.ts:39` — `GET /api/notifications › reads at most the 50 newest rows while counting every unread` and `alerts.feed.service.db.test.ts › reads at most the 50 newest rows while counting every unread`; the page (S7) reads the same `ALERT_PAGE_SIZE`.
- `GET /api/notifications` answers `{notifications, unreadCount}` with guarded rows and the caller's whole unread count — `src/routes/api/notifications/+server.ts:14` — `GET /api/notifications › answers the caller feed newest first, guarded, with the unread count`.
- Mark-read and mark-all are scoped to the caller's `userId`; mark-all touches only `readAt IS NULL` rows — `src/lib/server/db/actions/notifications.ts:61` — `POST /api/notifications › marks one row read, scoped to the caller`, `› marks every unread row read, scoped to the caller`, `› does not mark another persons row read`, `› is visible in the next GET: the row is read and the unread count drops`; and `alerts.repo.db.test.ts › markAlertRead ignores another persons row and an unknown id`, `› markAllAlertsRead stamps only the unread rows of the caller; read rows keep their stamp`.
- Pruning deletes only read rows and returns the count; unread Alerts are never pruned — `src/lib/server/db/actions/notifications.ts:81` — `POST /api/notifications › prunes only the caller read rows and returns the count`.
- The feed's write actions are ordered `all` → `pruneRead` → `id`; an unknown id is a silent no-op with `200 {success:true}` — `src/routes/api/notifications/+server.ts:40` — `POST /api/notifications › lets {all:true} win over {pruneRead:true}`, `› answers {success:true} for an unknown id and changes nothing`.
- `POST /api/notifications` answers `Invalid request body` only for a string, `null`, malformed JSON or empty body (the `isNotificationBody` guard is `typeof value === 'object' && value !== null`, so an array passes it and reaches the id check); an object with no usable action answers `Notification id is required` — `src/routes/api/notifications/+server.ts:29-33,46,66` — the `Invalid request body` and `Notification id is required` goldens in `POST /api/notifications` (the id-required table includes an empty array).
- Creating an Alert inserts, then fires a push with title = actor name, body = message and tap target `link`, or the page its type answers when it has none (`added_to_family` → `/family`, every task type → `/calendar/tasks`, Q-021), without awaiting it; a failed write is logged, never thrown — `src/lib/server/db/actions/notifications.ts:6` — `alerts.feed.service.db.test.ts › logs a failed write instead of failing the caller`, `› stores the Alert stamped with the ctx clock and fires its push`, `› taps an added_to_family push through to the family page`. Push is not contactable in tests; the row and the channel seam are asserted.
