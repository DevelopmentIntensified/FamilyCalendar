# groceries

**domain** — Grocery List (one list, scope filter), Grocery Items, Store Memory, Store Colours.

Domain words come from [CONTEXT.md](../../../../CONTEXT.md); use them exactly. Architecture rules: [docs/architecture/rules.md](../../../../docs/architecture/rules.md).

## Purpose

- Owns the **Grocery List**: one check-off list over both scopes with an All / Family / Mine filter (not two tabs), its Grocery Items (name + optional quantity + ordered store list), and the `/api/groceries` surface the Android app and the page both drive.
- Owns **Store Memory** (item-name → store learning that survives check-off and delete) and **Store Colours** (one swatch per Store, personal choice winning over the family one, then a name-derived default).
- Does not own family membership or the family id: the `family` domain supplies the viewer's family, and this module only asks for it. It does not compose the Day Dashboard's Groceries card (`dayDashboard` screen does), nor the tasks-page filter idiom it mirrors (`tasks` domain).

## Public interface

Everything other modules and routes may use, grouped by entry file. One line each: `name` — what it does.

- `index.ts`:
  - `GroceryItemResponse`, `GroceryListItem` (the page's row: the fields the list renders and edits, `createdAt` a `Date` from the loader or an ISO string from the wire), `GroceriesPageData`, `GroceryListScope` (`'mine' | 'family'`), `GroceryScope` (`{ userId, familyId }`: the list a read or write acts on, and the viewer a colour resolves for), `GroceryScopeFilter` (`'all' | 'family' | 'mine'`), `StoreColour`, `StoreColourRow`, `GroceryStoreGroup`, `GroceryGroup`, `GroceryCheckedEntry`, `GroceryApi` — the module's words as types; the wire schemas and their inferred types live in the contract file and are re-exported.
  - `parseGroceryQuickAdd(input)` — `"milk 2"` / `"2 milk"` / `"Eggs 6"` → `{ name, quantity }`.
  - `normalizeGroceryName(name)` — the history key (trim + lowercase).
  - `cleanGroceryStores(stores)` — trimmed, blanks dropped, case-insensitively de-duplicated, first spelling and first position kept. One home for the write-path clean and the chip read-path dedupe.
  - `mostFrequentGroceryStore(rows)` — the Store Memory suggestion; ties go to the first row seen.
  - `matchingGroceryMemoryRow(rows, store)` — the remembered row a trained store lands on (case-insensitive), else `null` and a new row starts at count 1.
  - `clampGroceryQuantity(quantity)` — floored, never below 1; an absent quantity is 1.
  - `grocerySuggestionName(query)` — the name a `GET /api/groceries?suggest=&name=` suggests for (legacy truthiness: an empty `suggest` asks for nothing), or `null` for the plain list.
  - `groceryChangeOf(body)` — the one runnable PATCH op (`check`, `uncheck`, `stores` with a list, `move` to `mine`/`family`), or `null` for the `op must be …` 400; an empty `stores` list is a real op (Q-037).
  - `groceryStoreGroups(items)` — the store groups without a colour, for a caller that only shows names (the Day Dashboard card); the same grouping rule `groupGroceryItems` builds on.
  - `groupGroceryItems(items, rows, scope)` — the store groups, each with its resolved colour: grouping and colour are one concept (#115) so no caller re-assembles them from two key conventions. `scope` is the viewer (`{ userId, familyId }`).
  - `resolveGroceryStoreColour(name, rows, scope)` — personal → family → name-derived default; `null` when there is no store to colour.
  - `groceryStoresSharingColour(name, names, rows, scope)` — the twins on one swatch, so a collision is disclosed rather than prevented.
  - `STORE_COLOURS`, `isStoreColourKey`, `groceryStoreKey`, `defaultGroceryStoreColour` — the closed six-swatch palette and its key/default rules.
  - `groceryColourOverrideKey`, `hasGroceryColourOverride`, `applyGroceryColourOverrides` — the optimistic colour map, keyed by scope AND store so one flip cannot re-label another scope's answer; `groceryColourScopeOf(raw)` — which row a colour write names (only the exact string `family` is the family's).
  - `GROCERY_SCOPE_FILTERS`, `groceryScopeFromParam`, `groceryScopeOf` — the one list's filter vocabulary and a row's own scope; `GROCERY_API_SCOPES`, `isGroceryListScope` — the wire's two scopes (`mine`, `family`) and their guard.
  - `matchesGrocerySearch(item, query)` — trim + lowercase, empty matches all, name OR any store.
  - `createGroceryApi(client)` — the browser client (kernel api client, K-07): `list`, `suggest`, `add`, `change`, `remove`, `colours`, `setColour`; typed from the contract, no UI state, no `fetch` in components.
  - `GroceriesListState` — the page's client state class; `new GroceriesListState(api, toasts, data, { scopeParam, schedule })`, then its methods (`setFilter`, `add`, `check`, `uncheck`, `saveStores`, `move`, `removeItem`, `setColour`, …) and its `$derived` views (`visibleItems`, `groups`, `colourStores`, `emptyCopy`, …).
- `index.server.ts`:
  - `listGroceryItems(ctx, actor, { scope })` — the open items of one scope, oldest first.
  - `suggestGroceryStore(ctx, actor, { scope, name })` — the remembered store, or `null`.
  - `createGroceryItem(ctx, actor, input)` — quick-add → a stored item (auto-filled store, trained memory).
  - `updateGroceryItem(ctx, actor, input)` — one use-case for check / uncheck / replace stores / move.
  - `deleteGroceryItem(ctx, actor, { id, scope })` — remove the row, keep Store Memory.
  - `listGroceryStoreColours(ctx, actor)` — every colour row the viewer can resolve against (`{ colours, palette }`).
  - `setGroceryStoreColour(ctx, actor, input)` — write or clear one store's colour in one scope.
  - `loadGroceriesPage(ctx, actor)` — the page's whole read in one call: the two item legs (`mine`, `family`) and the colour rows, each degrading to `[]`, plus the rail's own fields — `hasFamily` (drives the "Add to" Family option and the "No family yet…" line) and the viewer's `userId`/`familyId`; returns `GroceriesPageData` from the contract, so `ui/` can type its props.
  - `GroceriesPageData` — the page model type (`mine`, `family`, `colours`, `hasFamily`, `userId`, `familyId`), re-exported from the contract.
  - Endpoints: `listGroceryItemsEndpoint`, `createGroceryItemEndpoint`, `updateGroceryItemEndpoint`, `deleteGroceryItemEndpoint`, `listGroceryColoursEndpoint`, `setGroceryColourEndpoint`.
- `ui/index.ts`:
  - `GroceriesScreen` — the page body: builds the state class, lays the rail's three cards beside the one list, mounts the `Toaster`. Takes `data`, the raw `scopeParam`, and an optional `api` (tests).
  - `GroceryRow` — checkbox, name ×quantity, the Mine/Family badge, every store as its own coloured chip ("or" before alternates, primary ringed), edit/move/delete.
  - `GroceryGroup` — colour bar + dot, `<n> items · <total> total`, collision line, and the inline Colour picker with Everyone / Just me.
  - `GrocerySideRail` — scope chips with counts, search with its hint and clear button, quick-add with the visible "Add to" scope, the Store Memory chip and the `known-stores` datalist.
  - `GroceryCheckedRail` — what was checked off this session, struck through with its scope badge, unchecking on the scope it came from.
  - `StoreColoursCard` — every shop with its dot, a palette + Auto select per shop, one Everyone / Just me select, the collision line and the empty state.

**Deletion test.** Every export above hides a rule, not a body: `groupGroceryItems` would need the one-key convention and the three-tier colour merge re-pasted at each call site; `updateGroceryItem` would need scope resolution, the op switch and the memory training copied into the route; `loadGroceriesPage` would need three parallel legs and three fallbacks in `+page.server.ts`; `GroceriesListState` would need the optimistic write, its rollback and its local list edit re-pasted into five components. Nothing here is a pass-through: no export only renames another, and the page-owned state lives in `groceries.list.state.svelte.ts`, not in exports.

## How to test

- Whole module: `npm run test:mod -- groceries` (add `--legacy` while the legacy actions test remains).
- Pure rules: `groceries.items.rules.test.ts`, `groceries.colours.rules.test.ts`, `groceries.scope.rules.test.ts`, `groceries.list.rules.test.ts` — tables of input → expected output, no setup.
- Database + repo: `groceries.repo.db.test.ts` with `rollbackTest` (needs Postgres: `docker start familycalendar-db`).
- Services: `groceries.service.db.test.ts` with `rollbackTest` + `testCtx({ db })`.
- HTTP contract: [groceries.http.db.test.ts](groceries.http.db.test.ts) pins status, full body and observable rows of every endpoint, in committed mode (`beforeEach(truncateAll)`) because the legacy handlers write through the `db` singleton.
- State: `groceries.list.state.test.ts` drives the runes class with a fake api and `memoryToasts()`; no DOM, and the suggestion debounce runs on `manualScheduler`.
- UI: `ui/*.svelte.test.ts` render with props; the page itself is pinned by the visual check (`npm run visual:check -- groceries`).
- Fixtures: `groceries.fixtures.server.ts` (item / memory / colour / family builders).
