# marketing

**domain** — Public site: home, features, pricing display, roadmap/changelog, contact, SEO tags, Android/F-Droid page.

Domain words come from [CONTEXT.md](../../../../CONTEXT.md); use them exactly. Architecture rules: [docs/architecture/rules.md](../../../../docs/architecture/rules.md).

## Purpose

- Owns the signed-out public site: the content pages, their share metadata (one SEO table), contact intake, the pricing display and the signed-in `/checkout` page.
- Owns the `(marketing)` group's prerender/SSR flags, its chrome (the shell the pages render in) and the `/android` view of the committed publish record `src/lib/fdroid/published.json`.
- Does not own: `/login`, `/signup`, `/forgot-password`, `/reset` behaviour (identity) — marketing only carries their SEO rows and links; the plan amounts, discounts and the checkout quote (billing's services) — marketing owns the `/pricing` and `/checkout` pages and renders billing's numbers; the app chrome for signed-in app routes (shell) — marketing owns its own public HEADER (the legacy navbar: the public four for guests, the app's destinations for a signed-in visitor), rendered by the group layout.

## Public interface

The names below are the design the port builds on, and they all exist since S7. Each export earns its place by the deletion test. `marketing.contract.ts` (the contact body and responses) and `marketing.mail.rules.ts` (`CONTACT_RECIPIENT`, `contactSubject`, `isContactEmail`, `contactMessageHtml`) are imported by the service and the handlers inside the module and are not exported to other modules.

- `index.ts`:
  - `pageSeo(origin, pathname)` — the shell's single call: `{ title, description, canonical, meta }`, with `robots: noindex, follow` for the transactional paths. `pageTitle(pathname)` is its title half, the string a page renders. Delete them and the table lookup, the absolute-URL rule, the noindex rule and the title/row agreement move back into the pages — the drift the SEO test exists to stop.
  - `marketingPageOptions(adapter: string)` — `{ prerender, ssr }` for a `(marketing)` route: both on for `'static'`, both off for anything else. `CONTENT_PAGE_OPTIONS` is the always-on pair for `/changelog` and `/roadmap`. Delete them and the adapter rule plus its two overrides live in three route files that no test can import.
  - `MARKETING_NAV`, `CHANGELOG_ENTRIES`, `changelogNewestFirst(entries)`, `ROADMAP_SECTIONS` — the curated content: the fixed four nav links, the changelog (written newest-first; `changelogNewestFirst` is the stable sort the page uses), exactly three roadmap sections. Delete them and the data lives in a page nobody can check. Changelog dates format through kernel/time's `formatLongDate(date, 'UTC')` (`MMMM d, yyyy`, which is the legacy `Intl` output) — no local formatter.
  - `androidRelease(published: PublishedRepo)` — the `/android` view model (repo link, QR path, grouped fingerprint, APK size); the record is a parameter, the page load reads `src/lib/fdroid/published.json`. Delete it and the fingerprint/URL rules end up in the template.
  - `featureIcon(name: FeatureIconName)` — a closed icon vocabulary (`FEATURE_ICON_NAMES`); returns the tile colours and the SVG markup, the literals stay private.
  - `createContactApi(fetcher?)` — the browser client for the one contact wire; returns `{ send(fields) }`, where `send` resolves `{ok:true}` or the wire's sentence. Delete it and the page grows its own fetch and its own error copy.
- `index.server.ts`:
  - `contactEndpoint` — `POST /api/contact` as one use-case: rate limit (`contact` scope, 3/15 min), form parse, validation order, mail. A mail-provider failure is thrown as a **fault**, not an `AppError`, and the endpoint's `failMessage` carries the legacy 500 copy — so the wire matches and the kernel files the fault, exactly as the legacy `apiError` did. Delete it and the route reproduces the wire by hand.
  - `sendContactMessage` (the service behind it) is the module's reference shape for a **public anonymous surface**: `(ctx, actor: Actor | null, request)`, so the budget is spent before the form is read, exactly as the legacy gate ran. Identity's and access's anonymous entry points reuse that shape rather than inventing a second anonymous writer.
  - `marketingLayoutLoad` — `origin`, `pathname`, `isLoggedIn`, `user` and `year`. The self-referencing origin is the rule; a hardcoded domain is the bug it prevents.
  - `androidPageLoad` — `{ release }` from the committed publish record.
  - `pricingPageLoad` — `{ memberLimit }` for the free card, from billing's `FREE_PLAN_LIMITS`, and the `pricing_view` log line for a signed-in visit. Delete it and the member number and the event move into the page.
  - `checkoutPageLoad` — signed-in only (302 `/login?redirect=/checkout`, the legacy way back); `selectedPlan`, billing's `getCheckoutQuote` and `listEligibleDiscounts`, the family member count read as the fullest family's (Q-017 B) through family's `listFamilies`. Delete it and the quote arithmetic or the family read ends up in the template.
  - `checkoutPurchaseAction` — `POST /checkout?/purchase`: the legacy three sentences (`Not authenticated`, `Invalid purchase data`, `Checkout is not yet available.`) and no provider call, because the legacy stub had none. `optional` auth because the legacy action answered a success body, not a 401.
  - `strayRootPostAction` — #276: a `POST /` answers 303 back to `/` and logs the sender hints instead of a 405 error page.
- `ui/index.ts`:
  - `MarketingShell` — the group's chrome; the layout renders it with `MarketingHeader` as a snippet prop. The header components are imported by the layout file directly, not through this barrel, so a page that never renders them never pays for them (ADR 0010).
  - `HomeScreen`, `AboutScreen`, `AndroidScreen`, `ChangelogScreen`, `CheckoutScreen`, `ContactScreen`, `FeaturesScreen`, `PricingScreen`, `PrivacyScreen`, `RoadmapScreen` — one page body per route, so each route's `+page.svelte` stays a single render (R8).
  - `FeatureCard`, `MomentCard`, `GalleryCard`, `TestimonialCard`, `StrugglePanel`, `PricingCard` — the cards the pages compose; each has a visual baseline, so they stay components rather than inline markup.

## How to test

- Whole module: `npm run test:mod -- marketing` (add `--legacy` while legacy tests remain).
- Pure rules: `*.rules.test.ts`, plain tables of input → expected output, no setup.
- Database + services: `*.db.test.ts` using `rollbackTest` and `testCtx({ db })` (needs Postgres: `docker start familycalendar-db`).
- HTTP contract: [marketing.http.db.test.ts](marketing.http.db.test.ts) pins status + body of `POST /api/contact` (golden tests).
- The golden drives the wired route file directly (`actions.default`), which resolves to `contactEndpoint`; the mail goes to the ctx's memory mailer, so it needs no network and no credentials. It asserts the HTTP contract only; the mail's copy and escaping are pinned by the service test. Each test that depends on a budget shares **one** `ctx` across its requests: the limiter lives on `ctx`, and a fresh ctx per request would start every bucket empty.
- UI: `ui/*.svelte.test.ts` render with props (the cards through `FeaturesScreen`); state classes are tested without a DOM. Pages: `npm run visual:check -- marketing` compares each page with the baseline, `npm run perf:check -- marketing` checks the load budget.
