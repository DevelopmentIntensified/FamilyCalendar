# dashboardModules

**domain** — Dashboard Module registry, family master switches, per-user hides, the one visibility answer.

Domain words come from [CONTEXT.md](../../../../CONTEXT.md); use them exactly. Architecture rules: [docs/architecture/rules.md](../../../../docs/architecture/rules.md).

## Purpose

- **Owns:** the canonical Dashboard Module registry (one list: id, label, scope, band, meaning); the family master switches (`dashboardModuleSwitches`) that admins flip; the per-user hidden ids saved on the user's settings row; `dashboardVisibility`, the one composition that answers "is this module visible to this viewer, and which expensive read may the loader skip?"; and the family-hub row vocabulary ("Family-wide · Off", the chip tone, the value a click submits).
- **Does not own:** the user settings row itself (identity owns `userSettings`; the hidden list is read and written through identity's public interface), the family role check (`family` owns it; this module asks for admin), the dashboard page and its loader (`dayDashboard` calls the visibility answer and renders the data), or what a module displays — `meals` stays a registry id with no card (owner Q-002) because the id is saved state and retiring it would change `/api/dashboard` and the family switches.

## Public interface

Everything other modules and routes may use, grouped by entry file. One line each.

`index.ts`:

- `DASHBOARD_MODULES` — the canonical registry in its fixed order: `{ id, label, scope, band, meaning }` per module. Deleting it copies eight literals into every screen, so it stays.
- `selectDashboardModules({ scope?, band? })` — the registry filtered for one page (the account page's info and card bands, the family hub's family-wide rows). One predicate, so a wrong filter cannot silently show a customer the wrong switch.
- `isDashboardModule(id)` — the canonical check. The per-user save uses it to drop retired ids; a saved list naming one must never resurrect it.
- `canonicalHiddenModules(ids)` — the per-user save's pure canonicalization: canonical ids only, in registry order, duplicates collapsed, unknown and retired ids dropped silently (Q-029). One home, so the service and the account page's form action cannot disagree on what gets stored.
- `showsModule(map, id)` — reads a visibility map that came off a payload; an absent map or entry is **visible**.
- `dashboardVisibility({ settings, familySwitches })` — **the module's core**: one pure answer for one viewer, `{ modules, shows(id), needs(read) }`. Every id is present in `modules`, so a loader, a page payload and a component all derive from this and nobody composes two booleans again.
- `describeDashboardModuleRow({ scope, enabled, hiddenForViewer })` — one row's whole story: `{ state, scopeLabel, stateLabel, stateClass, submitValue }`. Family-off outranks hidden-for-me, a personal module never reads hidden-for-me (legacy parity, kept as an S7 decision), and the submit value is the opposite of the current family switch.
- `describeDashboardModuleState(scope, state)` — the same chip vocabulary when the state is already known (an optimistic override): `{ scopeLabel, stateLabel, stateClass }`. One table behind both, so a caller never re-derives the words.
- `dashboardModuleToggleValue(enabled)` — `'true'`/`'false'`, the value a click submits (the opposite of the current family switch). The family page's plain form uses it; `describeDashboardModuleRow` builds its `submitValue` from it.
- `createDashboardModulesApi(client?)` — the browser client for both endpoints (`setFamilyModuleSwitch`, `saveHiddenModules`), typed by the contract and returning `ApiResult`. The `account` and `familyHub` screens use it; nothing fetches by hand.
- Types: `DashboardModule`, `DashboardModuleId`, `DashboardBand`, `ModuleScope`, `DashboardModuleFilter`, `ModuleSwitchMap`, `ModuleRowState`, `ModuleToggleValue`, `DashboardModuleRowInfo`, `DashboardModuleChips`, `DashboardModulesApi`, `DashboardRead`, `DashboardSettingsFacts`, `DashboardVisibility`.
- Contract (zod schemas, each with its inferred type): `FamilyModuleParams` (the `{id}/{module}` route parts), `FamilyModuleSwitchBody` / `FamilyModuleSwitchResponse` (`PUT /api/families/{id}/modules/{module}`: `{ enabled: boolean }` → `{ success: true }`), `MyDashboardModulesBody` / `MyDashboardModulesResponse` (`PUT /api/me/dashboard-modules`: `{ hidden: string[] }` → `{ success, message, hidden }`), and every message the two routes add: `FAMILY_MODULE_ENABLED_MESSAGE`, `FAMILY_MODULE_FORBIDDEN_MESSAGE`, `FAMILY_MODULE_REQUIRED_MESSAGE`, `MY_MODULES_HIDDEN_MESSAGE`, `familyModuleUnknownMessage(id)` and `familyModuleNotFamilyScopedMessage(id)`.
- `dashboardModulesSavedMessage(hiddenCount)` — the per-user save's `message` (`Dashboard modules saved — 6 of 8 cards on.`). Wire copy, so it has one home beside the schemas instead of in the service and again in the account page's form action.

`index.server.ts`:

- `getDashboardVisibility(ctx, actor, { familyId })` — the read use-case: identity's settings row plus this module's family switches, composed by `dashboardVisibility`. This is what the Day Dashboard loader and `/api/dashboard` call. Its ctx is `DashboardModulesVisibilityCtx` (`Ctx & IdentityPorts`), because identity's settings service takes its own two ports attached.
- `listFamilyModuleSwitches(ctx, familyId)` — the persisted half: every family-scoped id seeded `true`, then the OFF rows applied. `family` reaches it through its `moduleSwitches` port (Q-030).
- `setFamilyModuleSwitch(ctx, actor, { familyId, module, enabled })` — creator/admin only (the role check, through family's `getViewerRole`, runs before the module name), then the registry decides unknown vs personal; a row exists only while OFF, so enabling deletes it.
- `saveHiddenModules(ctx, actor, { hidden })` — canonicalizes the posted ids, writes them on the user's settings row (identity), and returns `{ hidden, message }` with the wire's card count.
- `putFamilyModuleSwitchEndpoint`, `putMyDashboardModulesEndpoint` — the two `/api` handlers; route files stay wiring only.

`ui/index.ts`:

- `DashboardModuleRow` — the family-hub switch row: label, scope chip, state chip. It holds no state of its own: it submits `module` + `enabled`, carries `aria-pressed`/`aria-busy`, and accepts an optimistic override plus an acknowledge callback from its owner. Props in, callbacks out: the route passes the framework's `enhance` action (the component imports no `$app/*`) and the caller's submit callback; with neither, the plain form still posts to `?/toggleDashboardModule`. The chips read `describeDashboardModuleState`, so an optimistic state gets the same words and tone.

Module-internal, exported from no entry file: `readFamilyModuleSwitches(db, familyId)` and `writeFamilyModuleSwitch(db, { familyId, module, enabled, now })` with its `FamilyModuleSwitchWrite` type (the repo; the service re-exposes them as `listFamilyModuleSwitches` / `setFamilyModuleSwitch`, so the repo names differ on purpose: one exported name, one home, rule R11), and the fixtures.

## How to test

- Whole module: `npm run test:mod -- dashboardModules` (add `--legacy` while legacy tests remain).
- Pure rules: `*.rules.test.ts`, plain tables of input → expected output, no setup: the registry, `dashboardVisibility` and the row vocabulary.
- Wire schemas: `dashboardModules.contract.test.ts` — parse tables for both PUT bodies and responses (the one 400 copy per route, absent vs null vs wrong type) and the saved-message copy.
- Database + services: `dashboardModules.repo.db.test.ts` and `dashboardModules.service.db.test.ts` using `rollbackTest` and `testCtx({ db })` (needs Postgres: `docker start familycalendar-db`).
- HTTP contract: [dashboardModules.http.db.test.ts](dashboardModules.http.db.test.ts) pins status + body of both endpoints in committed mode (`beforeEach(truncateAll)`), because the legacy handlers write through the `db` singleton.
- UI: `ui/DashboardModuleRow.svelte.test.ts` renders the row with props and a capture fake for the framework's `enhance` action; no `vi.mock`, no `$app/*` import.
- Fixtures: `dashboardModules.fixtures.server.ts` — `seedFamilyWithRole`, `seedFamilySwitch` (S4).

## Invariants

Behaviour that must not change, each with the test that pins it (`file › test title`):

- The canonical registry is one list in one order — `verse` (personal, info) then `glance`, `top3`, `completed` (personal, card), `board`, `kids`, `groceries`, `meals` (family, card) — `src/lib/dashboardModules.ts:19-34`; `dashboardModules.registry.rules.test.ts › keeps the canonical ids, scopes and bands in one fixed order`.
- The id is the saved state: moving a module between bands keeps its id; a retired id is rejected and inert, never resurrected, and no data migration is owed — `src/lib/dashboardModules.ts:11-17,51-53,144`; `dashboardModules.registry.rules.test.ts › rejects a retired id and keeps every pre-move id canonical`.
- **Absent is not hidden**: no map, no entry, or a non-canonical id leaves a module visible; only an explicit `false` hides it — `src/lib/dashboardModules.ts:59-67`; `dashboardModules.registry.rules.test.ts › treats an absent map, an absent entry and an unknown id as visible`.
- `dashboardVisibility` composes once and purely: the family master switch applies only to family-scoped modules, the viewer's hidden list applies to every module, and every canonical id is present in `modules` — `src/lib/dashboardModules.ts:135-168`; `dashboardModules.visibility.rules.test.ts › composes the family switch and the hidden list into one total map`.
- **Family-off outranks the viewer's preference**: hiding or showing for yourself never lights up a module the family switched off — `src/lib/dashboardModules.ts:145-151`; `dashboardModules.visibility.rules.test.ts › a family-off switch wins over any user preference`.
- The Daily Verse is gated by its module **and** `settings.showDailyVerse === true`; no settings row means no verse — `src/lib/dashboardModules.ts:159`; `dashboardModules.visibility.rules.test.ts › no settings row means no verse — the setting is the gate, not a default-on`.
- `needs(read)` is true while any visible module consumes the read, so a loader skips an expensive read only when nothing on screen needs it; `top3`/`completed` declare no read because they consume the always-fetched user tasks — `src/lib/dashboardModules.ts:86-104,165-166`, `src/lib/server/services/dashboardData.ts:129-130`; `dashboardModules.visibility.rules.test.ts › needs() follows the visible consumers, not the module count`.
- Persisted switches are per family-scoped module and **rows exist only while OFF**: the read seeds every family module `true` then applies rows; enabling deletes the row; disabling inserts one, stamped with the caller's `now`; an unknown or personal id is refused with the legacy message — `src/lib/server/db/actions/dashboardModules.ts:12-47`, `dashboardModules.repo.server.ts`; `dashboardModules.repo.db.test.ts › defaults every family-scoped module to on`, `› enabling deletes the row — a row exists only while OFF`, `› disabling inserts the OFF row stamped with the caller now`, and `dashboardModules.http.db.test.ts › PUT /api/families/{id}/modules/{module} › re-enabling deletes the row — a row exists only while OFF` and `› rejects an unknown module id with the legacy message`.

## Depends on

- May import: kernel + identity, billing, alerts, family (public entries only).
- Owns tables: `dashboardModuleSwitches`.
- Reads (join only): none — the per-user hidden list and `showDailyVerse` are read through identity's settings service, not by joining `userSettings`.
- Declares no port: family is rank 4, so the one family fact this module needs — the viewer's role on a switch — is a direct import (`getViewerRole`). It implements family's `moduleSwitches` port (Q-030); the adapter lives in `src/lib/app`.
- Calls: `identity` — the user's settings row (hidden ids, `showDailyVerse`) and its write; `family` — `getViewerRole` for the admin/creator gate. Nothing else: visibility is pure.
- Called by: `dayDashboard` (the screen loader and `/api/dashboard` call `getDashboardVisibility` and use `needs()` to skip reads); `familyHub` (`listFamilyModuleSwitches`, `setFamilyModuleSwitch`, the row vocabulary and `ui/DashboardModuleRow`); `account` (`selectDashboardModules`, `saveHiddenModules`); `family` for the `moduleSwitches` map on `GET /api/families/{id}` — Q-030 answered **port**, so family declares the port and `src/lib/app` wires it to `listFamilyModuleSwitches`.
